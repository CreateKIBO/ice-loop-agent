# v3.18 整体优化（2026-11-08）

v3.4–v3.17 连续加功能之后，做了一次整体检查：引擎热路径用 200 篇文章（每篇 40 段）的临时数据逐个计时，界面看长列表与重复计算，代码看这几轮新增的重复片段，文档补一个索引。

## 测量

| RPC | 优化前 p50 | 优化后 p50 |
|---|---|---|
| `documents.list`（200 篇） | **145 ms** | **5.8 ms** |
| `documents.get` | 2.3 ms | 不变 |
| `documents.save_working` | 1.8 ms | 不变 |
| `skills.get` / `skills.resolve` | 2.6 ms | 不变 |
| `documents.suggestions` / `calendar` / `trial_status` | 1–2 ms | 不变 |
| `bootstrap` / `chat.list` | 2.6–2.8 ms | 不变 |

“优化后”是缓存已建立时的数字。应用启动后第一次列出文章要逐篇统计，耗时与优化前相当；之后只有改过的文章重新统计。`tools/perf-v3-documents.py` 新增 `list_documents_cold` / `list_documents` 两项（`--list-docs` 篇数，默认 200）。

除了 `documents.list`，其他方法都在 3ms 以内。`documents.list` 会被文章首页、左栏卡片和 AI 生成中的轮询（每 4 秒）调用；原来每次都把所有文章的正文 JSON 解析一遍，再统计摘要、字数、图片数和封面，耗时随篇数线性增长（1000 篇约 0.7 秒）。剖析显示 80% 的时间花在字数统计的正则上。

## 改了什么

1. **列表派生信息按 `content_hash` 缓存**（`documents/store.py`）
   - 摘要、字数、图片数、封面只取决于正文。按正文哈希缓存，最多 5000 条（LRU）。
   - 列表查询不再读取正文列，只有未命中缓存的文章才单独读一次。
   - 所有写入路径（保存、助手采纳、恢复版本、生成写回）都会更新 `content_hash`，所以内容一变，列表里马上是新数字；搜索仍按标题和摘要匹配。
2. **文章首页分批渲染**（`ArticleHome.tsx`）
   - 每行都有进入/布局动画，几百行一次性挂载会明显卡顿。改为先显示 60 篇，底部有「再显示 60 篇」「全部显示」。
   - 换视图、搜索或切换公众号后回到第一批。批量“全选”仍按全部文章计。
3. **重复代码收拢**
   - `application/documents.py` 新增 `_store()` 上下文管理器，替换 v3.16/v3.17 里三处手写的“打开连接—try—finally 关闭”。
   - `SkillSettings.tsx` 的“上次保存的技能”改为随保存结果计算一次，不再每次渲染都解析整份设置。
4. **基准工具**：`tools/perf-v3-documents.py` 增加文章列表的冷/热两项。
5. **文档索引**：新增 [v3 文档索引](README.md)，列出每轮迭代文档、对应的验收清单章节、代码地图和全部自动测试命令。

## 检查过、暂不改的

| 项 | 结论 |
|---|---|
| 每次请求新开数据库连接 | 打开 + 关闭约 1.8ms，相对模型调用可以忽略 |
| 前端轮询频率 | 左栏 20–30 秒、首页 30 秒（生成中 4 秒）、助手提案 1.5 秒（仅生成中）；窗口在后台时 React Query 自动停止轮询；列表变快后无需再调 |
| 旧稿件列表 | 只查询旧草稿和旧任务的少量字段，与篇数成正比但很轻 |
| 大文件（`DocumentEditor.tsx` 53KB 等） | 拆分需要完整构建与回归，单列为后续重构项，不在本轮做 |
| 测试耗时 | 全量约 50–70 秒，最慢的是真实子进程与 Chromium 端到端测试，属于必要成本 |
