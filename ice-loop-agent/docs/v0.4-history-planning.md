# v0.4：历史拟题、可编辑确认与发布进度

更新日期：2026-10-01。

本版把新建文章改为：选择公众号与栏目 → 自动读取发布进度 → 分析历史并拟题 → 采用或自行修改标题与需求 → 确认后开始写作。拟题和填充需求均不会自行创建任务。

## 1. 使用方法

### 首次登记发布进度

1. 重启桌面工作台，进入「发布记录与历史」。
2. 若文章已在本地，逐篇选择栏目、期号、发布状态；已发布文章填写实际发布日期，点击「保存登记」。可以展开正文核对。
3. 若已发布文章尚未导入，先用「快速设置已发布进度」。例如 PY 已发布至第 5 期，输入 5，新建 PY 文章默认第 6 期。JV、AI、WK 分别维护自己的进度。
4. 之后可在「草稿箱」通过本地导入按钮导入旧文章，再在历史页为它登记栏目、期号和发布状态。公众号的存稿目录也会自动纳入历史索引。

已有存稿、草稿箱文章和写作完成任务默认都是草稿，不会因为文件存在而被标记成已发布。登记操作仅记录本地状态，不会调用微信发布接口。当前也没有从微信公众号后台自动读取发布状态的连接。

### 新建下一篇

1. 切换当前公众号，点击「新建文章」。如果从栏目列表进入，使用当前栏目的默认期号。
2. 窗口显示已发布最大期号、建议期号、已登记发布文章数和草稿数。期号可以手动修改；「恢复自动期号」重新读取最新记录。
3. 直接点击「分析历史并拟题」，无需先手写标题。也可以输入一个想法作为方向提示。
4. AI 返回 3–5 个候选：标题、内容角度、读者收益、推荐理由及引用的历史文章。候选不会自动覆盖正在编辑的表单。
5. 点击「采用并编辑」带入标题与内容角度。收益和下期预告默认补全空白项；需要覆盖已填内容时勾选改写选项。标题、角度、收益、上一篇练习、预告和参考素材均可继续修改。
6. 还可以使用「AI 自动填充」完善其他需求。填写好的标题默认保留；标题上限 30 字。
7. 点击「确认需求并开始写作」。服务端核对当前公众号、历史版本和表单版本后才创建任务。

本版支持直接填写自己的标题并确认，不强制付费拟题。正式写作仍需要配置模型 Key；「体验离线示例」保持独立。

### 后续审核

表单的确认记录写入原来的 topic 审核门，决定者为 desktop-user，绑定确认内容的 hash。写作从已确认标题和内容角度继续，不会再次调用选题模型替换它。正文完成后，最终标题仍进入标题工坊供用户审核，以核对标题承诺与实际正文。

骨架、最终标题、配图计划、事实核验和代码执行等原有审核继续保留。新文章草稿不会推进发布期号；实际发布后需在历史页登记。

## 2. 期号与历史的规则

有效发布期号 = 同公众号、同栏目逐篇已发布记录的最大期号，与快速登记进度二者的较大值。下一期 = 有效发布期号 + 1。

| 情况 | 结果 |
|---|---|
| 没有发布记录，也没有快速进度 | 默认第 1 期 |
| 已发布 PY/005，同时存在 PY/009 草稿 | 默认 PY/006 |
| PY 已发布至 5，JV 已发布至 2 | 分别默认 PY/006、JV/003 |
| 只有快速进度 5，没有第 5 期正文 | 默认第 6 期，上篇练习留空 |
| 已发布记录 6，快速进度手动改为 4 | 有效进度仍为 6；需同时纠正误登记的已发布记录 |
| 新建期号已有草稿 | 提示先检查草稿；允许用户自行决定 |
| 有效进度为 9999 | 暂停新建，提示核对记录 |

全局文章文件夹编号不等于栏目的期号。比如 `009-文章标题` 内的入口文件标注 `AI/002`，历史记录识别为 AI 第 2 期。正文中提到的“上一篇 PY/001”不会被误识别为本篇期号。

登记已发布后保存该次正文快照；以后修改源文件，不会默默替换历史中的已发布正文。源文件保持只读。若登记错误，可改回草稿再纠正，草稿正文会跟随源文件刷新。

## 3. 本版实现

### 历史索引与数据来源

新增 `ice_agent/publication_history.py`。来源包括当前账号的存稿目录、文章任务及本地草稿箱；离线演示任务排除在真实历史之外。目录读取有大小和路径边界检查，禁止越过配置目录读取关联文件。

存稿正文按 `01-公众号正文-v2.md`、`01-公众号正文.md`、`正文.md` 顺序查找；期号只从首行栏目标识、文件夹明确的栏目编号或入口/发布说明首行识别，无法识别的记录等待人工登记。

已发布期号取整个索引的有效最大值。给模型的正文上下文有明确上限：当前栏目最近最多 6 篇已发布文章、3 篇草稿，以及最多 2 篇待归栏文章；每篇提供正文前 3500 字与结尾节选，另附最多 60 条历史标题。不是对所有历史全文作无限量分析；大量文章下可继续扩展摘要与检索索引。

上一篇练习和文末预告从与有效发布期号匹配的真实文章中提取；若仅有快速进度或缺失该期正文，练习留空，不让模型补造。历史文章同时带 published/draft 标记。标题或来源引用不符合结构约束时拒绝结果，模型文本与导入内容在界面中转义显示。

### SQLite 新表

| 表 | 作用 |
|---|---|
| publication_history | 账号隔离的标题、正文快照、栏目、期号、发布状态与来源键 |
| publication_progress | 各账号各栏目的手动发布进度基线 |
| publication_plans | AI 候选、历史版本、确认表单、确认 hash 与对应 job_id |

启动时通过 `CREATE TABLE IF NOT EXISTS` 追加，不修改旧文章与原审核记录，也不需要清空已有数据。

### API

| 方法 | 用途 |
|---|---|
| history.list / get | 读取本账号历史条目与正文 |
| history.update | 登记标题、栏目、期号、发布状态和日期；使用原 content_hash 防止覆盖过期记录 |
| history.progress | 设置栏目的已发布进度基线 |
| planning.context | 读取建议期号、历史标题/正文节选与 context_hash，不调用模型 |
| planning.propose | 根据真实上下文拟题，保存候选，返回 plan_id |
| planning.confirm | 保存用户最终修改的表单，返回 confirmation_hash；不会创建任务 |
| jobs.create | 使用确认版本建任务，记录选题审核；同一已消费 plan_id 重试返回原任务 |

桌面调用 `planning.confirm` 后才调用 `jobs.create`。服务端重新核对表单 hash、账号及历史 hash；栏目/期号与旧候选不匹配或历史发生变化时，要求刷新并重新确认。调用方伪造的确认来源和历史上下文不会写入正式任务，确认表单中的参考素材由服务端重新构造。

传统 CLI/直接 API 的未确认建任务通道保留原来选题审核，不会凭一个传入的“已批准”标记跳过审核。

### 模型路由与费用

历史拟题使用当前配置的「策划」角色，沿用国内供应商适配。未配置真实凭据时显示错误，不用离线示例冒充拟题成功。

一次拟题使用所选供应商，最多一次普通请求和一次结构修复请求，每次超时 40 秒，不自动切换供应商重试。拟题和需求填充发生在任务创建之前，因此不计入单篇任务的 model_calls 计数；多次主动点击会分别请求并可能产生费用。正式供应商的实际拟题质量与网络表现尚未使用用户付费模型验证。

### 桌面交互

新增 `desktop/renderer/planning.js`，提供历史管理、期号加载、候选卡片和显式确认。拟题返回时不自动修改表单；只有点击采用才替换标题与角度。等待加载期号时的手动修改优先保留。关闭窗口、切换账号/栏目或修改期号后，旧候选响应不会重新填入。

最终提交期间冻结表单控件，确保所见内容、确认内容与实际任务一致。任务保存 `article_history` 和公众号配置快照，后续写作与审核继续使用这份上下文。
