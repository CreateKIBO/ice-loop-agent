# v1.5 工作台体验调研与适配建议

调研日期：2026-10-04。范围：官方产品文档、官方开源许可证，以及本项目 v1.4.1 的 renderer 源码与实际截图。下文区分“产品已公开的能力”和“本项目建议”；建议不代表已经实现。没有读取真实模型凭据，也没有请求付费模型。

## 1. 从同类工作台吸收什么

| 参考 | 官方公开能力 | 本项目可采用的设计 |
| --- | --- | --- |
| LibreChat Artifacts | 生成结果在独立面板中展示，可以继续对话修改，并支持扩大预览 | 维持左侧讨论、右侧文章的结构，增加容易发现的专注预览、版本选择和明确交接按钮 |
| Open WebUI Notes | 编辑器旁边可开对话，选中文字可以交给 AI 修改，插入结果前创建版本 | 保留“候选稿 → 手动修改 → 审批”的安全链路，清楚展示选中文字、稿件版本和保存状态 |
| Open WebUI History & Search | 侧栏保存会话，可用 Ctrl/Cmd + K 搜索，支持归档与会话管理 | 用统一搜索入口找到会话、草稿和任务；侧栏提供最近项目，全部列表交给搜索和管理窗口 |
| Open WebUI Folders & Projects | 会话可以分组、折叠，并带关联上下文 | 将创作、内容资产、设置分组。公众号档案继续作为本项目的隔离边界，栏目和文章历史继续作为上下文 |

来源：[LibreChat Artifacts](https://www.librechat.ai/docs/features/artifacts)、[Open WebUI Notes](https://docs.openwebui.com/features/notes/)、[History & Search](https://docs.openwebui.com/features/chat-conversations/chat-features/history-search/)、[Folders & Projects](https://docs.openwebui.com/features/chat-conversations/chat-features/conversation-organization/)。这里只参考交互机制，未复制这些项目的源代码或整套框架。

本项目的核心仍然是公众号创作工作流。通用聊天工具的多模型讨论、代码沙箱、多人共享、复杂标签语法没有必要同时加入。本轮应把已有“讨论 → 初稿 → 保存 → 审批 → 配图 → 导出”的路径做清楚，而不是增加更多入口。

## 2. 当前界面最值得优先改善的地方

以下判断来自 `creative-chat.js`、`index.html` 和 `docs/screenshots/v1.4.1/chat-generating.png`，属于本项目观察。

1. 侧栏品牌头、按钮、十余导航、最近草稿和会话占用较大高度；整条侧栏需要滚动。收紧头部与行高，折叠低频设置，把最近草稿/会话置于一个可滚动区域，保留主导航和连接状态。
2. 文章区已经有版本、修改、审批功能，但是操作分散在面板上方和底部。增加简短的阶段提示与下一步入口，让用户知道当前是未保存候选、已存初稿、待审批还是已采用。
3. 输入框使用 `creative.text` 保存页面内文字，但是不同会话之间没有独立的输入草稿。如果改善，应按公众号 ID + 会话 ID 保存输入，并在发送成功后清空对应草稿；不要把用户的未发消息带到另一个公众号。
4. 引用文章显示为标签，文档标签有移除按钮，但文章标签和选中文段缺少同等清除入口。补充来源提示、移除操作、选中文段的字数，能减少误改整篇的困惑。
5. 消息列表已经判断是否靠近底部，但每轮重建 DOM。需要显式保持离底部较远时的阅读位置，再提供“回到最新”；不要用所有内容变化都自动滚到底部的动画。
6. 生成中的“真实阶段 + 接收字符数 + 用时”是有价值的，应继续保留。不能用虚假的百分比替代模型状态。
7. 界面动效需要围绕“哪里变了、操作是否成功”设计。让页面、弹窗、候选稿和阶段变化有短反馈，避免每个字或每次轮询都触发整页位移。

## 3. 动效库选择：Motion 的 JavaScript API

建议使用官方 `motion` npm 包的 `animate` 与 `stagger`，由现有 esbuild 打包到本地 renderer vendor。官方提供 JavaScript 入口，支持 HTML/SVG 与动画控制；因此本项目不需要先换成 React。Motion 主仓库使用 MIT 许可证，发行包应保留其 copyright 与 license。免费 API 已覆盖本轮需求；标记为 Motion+ 的能力和付费示例不应成为构建依赖。

来源：[Motion 安装与 JavaScript 使用](https://motion.dev/docs/quick-start)、[animate API](https://motion.dev/docs/animate)、[stagger API](https://motion.dev/docs/stagger)、[官方 MIT 许可证](https://github.com/motiondivision/motion/blob/main/LICENSE.md)。实际版本以本轮 package-lock 中的锁定值为准。

建议接入位置：

| 位置 | 动作 | 建议尺度 |
| --- | --- | --- |
| 主工作区切换 | 新页面淡入并轻移 | 160–220 ms，垂直 4–6 px |
| 弹窗或搜索面板 | 面板淡入，避免背景跟随缩放 | 140–180 ms |
| 列表首屏 | 按短间隔出现少量卡片 | 每项 20–30 ms，最多 6–8 项 |
| 新候选稿 | 一次轻淡入，提示可预览与保存 | 180–220 ms，不对全文逐字动画 |
| 生成状态 | 阶段切换有反馈，忙碌图标持续运动 | 阶段变化时触发，不能每次轮询重启 |
| 按钮反馈 | 明确 busy/disabled/成功状态 | 按键反馈短于 120 ms，不让按钮布局跳动 |

以上时长是本项目设计建议，最终应以原生窗口验收为准。避免动画字号、宽高、文字排版，优先操作 opacity/transform；不添加与品牌手册冲突的渐变、3D 或阴影。

## 4. 生命周期与减少动态效果

Motion 官方控制器提供 `cancel()` 和 `stop()`：取消会回到初态；停止会把 WAAPI 的当前值提交到 style。因而不能在每次 DOM 卸载时随意 `stop()`，否则可能遗留中间透明度或位移。短入场动画应有稳定的 CSS 正常态，动画结束或取消后界面都必须可见。每个效果保存自己拥有的控制器，只清理自己创建的动画，不调用全局 `document.getAnimations().forEach(cancel)` 干扰 Shoelace。

本项目是 vanilla JS，应该使用 `matchMedia('(prefers-reduced-motion: reduce)')` 和 `change` 监听实现系统偏好，而不是把 Motion 的 React hook 搬进来。如果增加“减少动效”设置，其有效状态应由用户设置与系统偏好共同决定。系统设置变化时停止持续旋转/脉冲并恢复静态正常态；有限入场可以快速完成。无限循环不应调用 `complete()` 假定存在终点。

来源：[Motion 控制器](https://motion.dev/docs/animate)、[MDN prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion)。这些生命周期策略是结合当前应用结构的适配判断。

当前 `paintCreativeProgress()` 每轮会替换内部元素，故要避免为相同阶段反复做整个进度卡入场。可以用“会话 ID + 助手消息 ID + phase”识别真正状态变化，给新图标分配循环控制器；节点移除时取消旧控制器。页面或公众号切换时清理动画、监听和定时器，不能让旧账号的动画回调改新页面。

## 5. 验收应覆盖体验而非只看截图

- 1366×768、1920×1080 与紧凑窗口下，输入、生成初稿、停止、保存与审批按钮可到达，预览没有横向溢出。
- 鼠标和键盘均能打开搜索、选择结果、取消弹窗并回到原焦点。
- 输入未发消息，切换会话再回来可恢复；切换公众号看不到另一个公众号的输入。
- 用户阅读旧消息时，流式回复不拉走阅读位置；回到最新按钮明确可用。
- 生成中禁用操作能恢复，取消与快速完成均不会留下半透明节点或仍在旋转的图标。
- 减少动态效果在启动和运行中切换都生效；仍然有可读的文字状态。
- 保存、审批、手动修改、版本冲突、归档/删除/恢复等 v1.4.1 链路继续可用。
- 所有库脚本本地打包；离线打开工作台不依赖动画 CDN。

本轮应先把这些交互跑通，再打包和核对 renderer 源文件与实际 ASAR。源码测试通过不等于打包程序已包含最新界面。
