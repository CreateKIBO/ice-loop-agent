# 工作台优先转向：产品架构评审与实施建议

日期：2026-11-05。评审基线：`aef025a`，当前分支 `codex/skills-settings-2026-11-05`。

后续收敛：Claude 独立评审及讨论已整理为[开发报告与实施基线](工作台优先转向-开发报告-2026-11-05.md)。本文保留首轮建议；其中六个一级入口、新AI稿必经候选采纳、预先选择结构化规范值、P0多套主题等，以新报告的修订为准。

本文整理用户提供的产品转向要求与本轮评审建议，属于产品与架构文档，不代表下述功能已实现。本轮不修改产品代码。

## 需求边界与已有能力

用户明确的方向：

1. 面向各类微信公众号，解除单一教学账号的专属约束。
2. 移除新任务中的代码运行、终端输出回填和终端截图功能。
3. 内嵌浏览器支持普通网页访问与收藏，TapNow 和微信后台成为可收藏的网站。
4. 文章工作台作为首页，AI 助手拥有独立入口。
5. 用户可以从已有稿件开始编辑文字、图片与排版；Agent 能读取授权稿件、提出修改和整理建议。
6. 保留整篇生成，支持手动、导入和 AI 生成内容进入共同的文章体系。

本次路线以 Windows、Electron、React/TypeScript、Python 引擎、SQLite、本地优先和人工发布为边界。此前讨论的云端授权自动发布方案应标记为另一阶段的可选规划，不作为本次转向的前置条件或完成承诺。

保留现有优势：公众号隔离、文章与资料、版本、候选比较、修改提案、备份恢复、模型路由与预算。当前 Skills 第一版已经实现按公众号选择、修改、启停、新建/移除主写作技能及快照；后续“规则包”沿用该机制，不另建平行系统。

## 1. 总体判断

支持这次转向。“文章工作台优先、Agent 辅助、保留整篇生成”能够形成连贯产品，因为三种入口都处理同一种对象：文章。

会造成两套产品的情况，是手写稿、导入稿与 AI 稿使用不同编辑器、资源库、版本或保存流程。应统一文章编辑与交付，把生成视为产生候选内容的后台任务。

当前方案同时承担编辑器、排版工具、浏览器和 Agent 平台四项工程，P0 过大。第一阶段的承诺应收敛为：已有稿件能够方便地整理、排版、配图和交付；需要时，AI 可以参与其中一段工作。

初期目标用户建议聚焦：已有稿件、长期管理一个或多个公众号的个人或小团队。删除代码执行符合这个目标，同时会失去原有技术教学特色；新的优势需要建立在本地文章资产管理、版本可追溯、可审阅的 AI 修改和稳定的公众号交付上。

## 2. 五项主要风险与缓解措施

| 优先级 | 风险 | 缓解措施 |
| --- | --- | --- |
| 1 | 内容和排版在导入、编辑及导出转换中丢失；现有 Markdown 回写链不能完整表达复杂布局 | 先确定文档规范、版本和兼容策略；保留导入原件与转换报告；不静默删除未知内容 |
| 2 | 范围失控，泛化后直接面对成熟排版编辑器，产品优势不清晰 | 首批聚焦明确用户；以已有稿件的完整交付验证价值；控制模板与浏览器功能规模 |
| 3 | Agent 修改破坏信任：覆盖新版、跨稿件操作或误删 | 修改绑定文章与基础版本；冲突保留双方内容；删除进回收站；支持撤销 |
| 4 | 通用浏览器带来登录、弹窗、下载、内存和兼容维护成本 | P0 实现地址栏、普通网页访问、简单收藏、外部打开；复杂标签组织和完整会话恢复后置 |
| 5 | 旧 AI 流水线继续支配保存、编辑与导出，工作台定位只有表面变化 | 手动文章生命周期独立于生成任务；没有模型配置也能完成编辑和基础交付 |

不以功能数量作为差异化。排版质量和用户完成一篇稿件的操作成本，比模板数量或内部节点数量更重要。

## 3. 推荐信息架构与默认流程

### 一级导航

| 入口 | 默认内容 |
| --- | --- |
| 文章，首页 | 最近编辑、搜索、筛选、草稿列表、新建文章、继续编辑 |
| 素材 | 图片、来源、使用记录、待归档下载 |
| AI 助手 | 整篇生成、对话、生成任务与候选 |
| 网页 | 地址栏、收藏、当前网页 |
| 发布记录 | 用户登记的时间、链接和对应文章版本 |
| 设置 | 公众号与品牌、写作技能、模型、存储与备份 |

首页采用紧凑列表，突出“继续编辑”。新建菜单提供“空白文章 / 粘贴文章 / AI 起草”，空白文章是默认操作。不要把模型配置或栏目、期号设置放在开始手动写作之前。

打开文章后，编辑器是主工作区。顶部显示标题、保存状态、预览和交付操作；排版与图片属性放在可收起面板。文章历史与 AI 修改建议一点击达；模型路由、预算细节和内部日志位于高级入口。

### 默认流程

已有稿件：粘贴 → 检查导入结果 → 编辑与排版 → 处理图片 → 复制或导出 → 微信后台保存/手机预览/发布 → 登记。

AI 起草：填写需求 → 后台生成 → 查看候选 → 采纳 → 进入同一个文章编辑器。

默认生成一份候选。两到三份候选作为用户选项，不默认增加费用和比较负担。后台任务完成后只做结果提示，不抢占当前编辑上下文。

## 4. 保护工作台定位的产品规则

- 不配置模型，也能新建、导入、编辑、保存、预览和导出文章。
- 启动进入文章首页；生成任务完成后不强制跳转。
- 手动文章不要求先创建生产任务，也不要求填写栏目与期号。
- AI 结果须经采纳才能改变现有正文；用户手动编辑正常自动保存。
- 文章、图片和版本不依赖某段聊天才能找到。
- 聊天、动效和任务面板不能抢占正在编辑的文章。
- 风格检查只依据当前启用的技能与品牌规则，未启用规则不成为阻断项。
- AI 操作显示读取范围、目标位置，支持取消、拒绝或撤销。
- 保存与草稿导出不以完成整条 AI 流水线为前提；检查结果不冒充事实已核验。

设计评审可用的指标：完成一篇已有稿件时，有多少步骤必须进入 AI 页面、等待模型或填写与文章无关的信息。这些强制步骤应为零。

## 5. Agent 与数据模型

### 上下文范围

| 上下文 | 默认处理 |
| --- | --- |
| 当前文章 | 使用最新保存或工作草稿快照，标明版本 |
| 选区 | 局部操作优先使用，避免无关全文被重复改写 |
| 钉选稿件 | 经用户选择后持续引用，可随时取消 |
| 检索资料 | 默认限定当前公众号，显示实际引用来源 |
| 技能与品牌 | 显示生效组合，生成时冻结版本 |

“前五篇正文＋全部标题”保留为系列续写的可选策略，普通文章按主题检索，并允许手动钉选。

发起 AI 操作前，先将所需工作草稿保存为可定位快照。选区与提案锚点必须对应该快照，不能把用户屏幕上的新内容与旧保存版本混用。后台任务固定所属公众号，不能随当前导航账号变化。

### 读写权限和操作语义

| 操作 | 用户体验与处理方式 |
| --- | --- |
| 查找、阅读、分析 | 在授权范围内执行，展示引用对象 |
| 新写一篇 | 自动保存为候选；采纳后进入正常草稿流程 |
| 改文字、增加段落、调整图片 | 针对具体位置提出修改提案 |
| 删除文章 | 展示对象与影响，经确认后进入回收站 |
| 永久删除 | 保留为用户直接操作 |

“所有写入都走提案”应修订：手动编辑、工作草稿自动保存和候选结果落盘正常执行；AI 修改现有用户正文时要求提案与采纳。

提案以段落或内容块为主，文字内部显示差异。样式提案显示属性变化，图片提案显示图片与裁切等变化。支持部分接受，但应用结果仍须通过结构校验。

应用提案时检查基础版本与当前工作内容。过期提案不能仅凭相似文字模糊定位后强行应用；冲突时展示双方内容，允许重新生成或人工处理。接受提案产生可撤销、可追溯的文章版本。

### 数据实体建议

| 实体 | 方向 |
| --- | --- |
| `articles` | 各种来源文章的共同入口；不强制绑定生成任务；记录来源与可选系列信息 |
| 工作草稿、`article_revisions` | 分开处理高频自动保存与稳定历史版本；正文结构、样式与图片引用共同进入版本 |
| `generation_runs`、生成输出关联 | 模型、费用、参数、任务状态与候选版本；候选复用文章文档结构 |
| `edit_proposals` | 复用已有机制，扩展到结构、样式和图片操作 |
| `assets`、文章资源引用 | 原始资源独立存放；每篇文章中的裁切、图注、顺序与排列单独记录 |
| `bookmarks`、浏览器会话元数据 | 收藏与登录会话分别管理；Cookie 仍由隔离的浏览器会话管理 |
| `publication_records` | 人工登记的链接、时间与交付版本；不能把已导出当作已发布 |

不要为手写稿、AI 稿和导入稿建立三套内容真相。候选可以拥有独立生命周期，但使用同一文档结构、编辑组件和资源引用机制。

新文档建议采用结构化规范，Markdown 作为兼容表示。旧稿通过版本化迁移逐步接入。复杂排版下，不承诺富文本和 Markdown 无限往返且完全无损；源码模式需明确哪些布局不能表达。

## 6. 修订后的 P0 / P1 / P2

| 阶段 | 包含 | 后置 |
| --- | --- | --- |
| P0：证明工作台成立 | 文章首页、独立手动草稿、基础粘贴、可靠保存/版本、基础排版、图片替换/图注、复制与图片包、普通网页访问/简单收藏、停用新代码执行 | Word 高保真导入、完整浏览器管理、建议收件箱、复杂 SVG、全文长图设计 |
| P1：Agent 融入工作台 | 完善生成任务、快速/引导模式、候选比较、局部提案、选区上下文、跨稿件检索、图片裁切/压缩、更多排版预设 | 大规模自动建议、复杂跨文章批量修改 |
| P2：长期运营效率 | 建议管理、素材标签、发布日历、复杂图文组件、长图/切片、批量整理 | 实时多人协作、完整浏览器替代品另行评估 |

D6 要求保留整篇生成，因此 P0 不能先拆掉现有生成能力，等 P1 再补回。P0 保留简化入口与可用链路，P1 完善任务和候选体验。快速模式输出候选与检查结果；引导模式在选题、骨架、标题等用户需要决策的位置停顿。

P0 的视觉预设先做两到三套，优先验证编辑与交付质量。发布日历首先用于规划与记录，不暗示支持自动定时发布。

### 五条端到端验收旅程

| 场景 | 完成条件 |
| --- | --- |
| 纯手动 | 无模型配置，粘贴稿件、编辑文字/图片、排版并导出，全程无需 AI 页面 |
| 恢复与迁移 | 旧稿、配图和历史可读取，退出重启后工作草稿恢复 |
| 局部 AI 修改 | 选中段落、获得提案、部分接受，其他段落保持，修改可撤销 |
| 整篇生成 | 生成时继续编辑另一篇；采纳后进入同一个编辑器，既有文章不被覆盖 |
| 人工交付 | 复制正文、按顺序上传图片、微信后台保存/手机预览；回来登记链接和对应版本 |

## 7. 开放问题的建议结论

### 整篇生成入口

文章首页的新建菜单保留“AI 起草”，与空白/粘贴并列；完整参数和任务管理放 AI 助手。既能被发现，也不会占据首页主体。

### 编辑器是否共享

共享一个编辑器。生成页面承担需求、进度和候选；采纳后的编辑、图片、版本和交付流程统一。

### 是否展示内部节点

普通界面展示“整理资料、生成正文、准备图片、检查结果”等摘要。详细节点放在可展开的执行记录中。需要用户决定时，给出具体动作。

### 收藏作用域

支持全局与公众号两层。通用工具可以全局收藏，专属页面按公众号收藏。全局收藏仅共享地址，不共享登录状态；登录会话继续隔离。

### 排版自由度

优先提供已验证的字号、行距、段距、颜色、标题、引用、列表和图片样式。复杂叠放、任意定位、外部字体与互动效果单独评估。行内样式是兼容处理的一部分，不代表本地网页效果可原样交付微信。

### 导入保真承诺

承诺尽量保留文字、结构和受支持样式，并提示变化。粘贴提供“适配当前样式”“仅保留文字”；“尽量保留原样式”须标明边界。

Tiptap 的 schema 决定允许的节点和属性，未定义内容可能被丢弃。Word 的主题、命名样式与局部格式叠加使视觉还原更复杂。不能承诺任意 HTML、Word 和公众号复杂排版无损导入。

复杂不支持模块保留原件或提供转静态图片选项，不静默删内容。粘贴保真、DOCX 文件导入和公众号链接导入是不同能力，分别列出支持范围与验收样本。云端文档转换不能默认隐藏在“本地导入”操作后面。

### 最小 P0

一篇已有稿件不依赖 AI 即可完成整理、基本排版、图片处理和交付；退出后工作不丢失。

## 8. 必须纠正或明确的事项

1. **节点数量**：列出的14个节点删除 verify_code 与 integrate_evidence 后为12个，不是11个。手动、局部修改与整篇生成不必使用同一条长流水线。
2. **写入提案边界**：手动编辑、自动保存和候选落盘正常执行；AI 修改现有正文须采纳。
3. **本地优先的准确表述**：文章库、图片、凭据和收藏本地保存；云端模型会接收被发送的上下文，网页访问产生网络请求。展示调用将发送的文章、选区和参考资料，不能宣称所有内容从不离开本机。
4. **代码功能退场**：关闭新入口、新任务的执行工具、队列能力及执行类门控；旧记录、截图、正文引用和导出文件保留可读。迁移后旧任务继续操作时，应进入明确的兼容/归档路径，不隐式重启执行。
5. **系列和期号可选**：保留旧值与原版本；普通文章不伪造栏目/期号，也不要求先建栏目。
6. **浏览器工程边界**：外部网页不能获得本地文件、凭据或工作台 IPC；通用访问要重新审查导航、弹窗、权限和下载边界，不能仅删除网址判断。
7. **交付验收**：检查复制粘贴后、后台保存后和手机预览后的结果；本地截图不能替代公众号实际验收。
8. **路线统一**：本次以本地制作和人工发布为准；此前云端授权、自动发布与云端多租户服务不列入当前转向验收。

### 旧数据迁移原则

- 迁移前备份，按 schema 版本演进，保留可验证的旧稿原件及映射。
- 旧教学账号的品牌和技能作为显式配置保留，不转为所有新用户的强制默认规则。
- 将系列、期号和历史上下文策略变成可选元数据/策略，不删除原记录。
- 新文档使用新结构；旧 Markdown 文章按需迁移。不能无提示重写全部历史正文或图片引用。
- 旧代码证据只读保留，和新写作流程解绑；旧审批和检查结论保留其版本身份，不当作新规则下的已审核结论。
- 已发布记录关联实际交付版本；后续编辑产生新版本，不回写原发布快照。

建议先验证“打开应用 → 粘贴已有稿件 → 编辑排版 → 交付微信”这一条主流程，再据此调整文档模型和页面结构。
