# 长会话与内存迭代验收

本批次已实现并验证长会话读取、历史浏览、候选稿访问与消息虚拟渲染。项目整体上线目标仍 active，不能用这一批测试代替真实供应商质量、完整桌面安装和升级验收。

## 问题与改动

旧实现每次 `chat.get` 都读取会话全部消息和全部候选稿，包括正文；新 UI 空闲每 8 秒、生成中每 1.5 秒刷新，同时挂载全部 Markdown。会话长度直接放大 IPC、解析、DOM 与缓存成本。

新 UI 默认每次读取最近 40 条消息、3 份候选稿。历史消息可向前、向后翻页并返回最新；候选稿独立翻页，旧稿仍能保存和提交审阅。已审批候选显示状态并禁止重复另存为未审批稿。翻页不会删数据库记录，也不会裁剪模型实际使用的上下文。

接口保持旧调用完整响应；新调用显式传 `message_limit` / `candidate_limit`。可选 `before_message_id` / `after_message_id` 与候选稿对应字段；限制分别 1–100 和 1–20，拒绝双方向、非整数和其他会话游标。返回 `message_page` / `candidate_page`：`oldest_id`、`newest_id`、`has_older`、`has_newer`。使用会话范围内稳定身份和 SQLite rowid 索引查找，避免时间相同时漏消息或 OFFSET 随新增消息漂移，不把 rowid 暴露给客户端。

消息区使用项目已有的 `@tanstack/react-virtual`，动态测量 Markdown，保留复制和再次使用。当前历史页、实时尾页与候选页分开查询；离开页面后即时释放对应查询缓存，不累计已经翻过的历史页。用户向上阅读时固定当前窗口，实时轮询仍继续，新消息用未读提示通知；返回底部再释放固定窗口。生成状态仍由实时尾页和事件流提供。

布局测量、宽高改变和用户滚动分别处理，避免测量事件误停自动跟随；内容区和滚动视口均通过 ResizeObserver 观察。滚轮、拖动、触摸及键盘支持阅读状态切换。

## 性能测量与边界

同一合成会话在服务层的单次对照：

| 指标 | 旧完整读取 | 新默认窗口 |
|---|---:|---:|
| 消息/候选数 | 2000 / 120 | 40 / 3 |
| UTF-8 JSON 大小 | 37,478,266 B | 759,231 B |
| 本次服务调用时间 | 100.49 ms | 11.36 ms |

此样本传输量减少约 98%。时间是本机单次合成样本，不承诺任意工作负载固定提速倍数，实际 IPC 包含额外开销，详见结果中的 `transport`。

长会话最终 JS 堆：预热 6,159,536 B，翻十页并回到实时 7,171,112 B，增长 1,011,576 B，DOM 从 636 到 500。该值经过显式 GC，用于观察仍被保留的对象，不表示进程会立刻向 Windows 归还所有内存。

所属 Electron / Python / conhost 全进程树工作集：短会话约 419 MiB、长会话预热约 439 MiB、翻页返回约 465 MiB。进程工作集包含 Chromium、分配器和代码缓存；不能把约 7 MB 的 JS 堆说成整程序只用 7 MB，也没有用这组数据证明全桌面 RAM 下降 98%。真实浏览器大页面、长时间图片操作仍需后续独立验收。

`sample-owned-memory.ps1` 已补进程创建时间检查：Windows 会重用 PID，单凭 ParentProcessId 可把更早启动的其他程序算成当前新进程的子进程。首次失败样本中的 Creative.App/Java/VMware 结果无效，已保留失败 evidence，最终统计只纳入当前拥有树。它只测量，不终止这些进程。

## 调试中发现的问题

1. 虚拟行挂载后高度变化被误认为用户上翻，导致会话未停在最新；现在只消费实际滚动意图，测量保持跟随。
2. 读实时窗口时，新增消息会挤掉窗口首行；现在固定阅读快照，实时结果另行更新。
3. 加载空白期间留下的滚轮意图、复制按钮点击及随后改变尺寸可能错误退出跟随；只在已有可滚动消息时记录意图，消费后立即清除，观察视口尺寸。
4. 第一版合成候选的 base 为空对象，保存被真实版本门拒绝；修正夹具为创建会话返回的实际 `current`，没有放宽生产校验。
5. 测试对带未读数量的“回到最新”按钮用了错误的全字匹配、对动态布局只等待固定时长；改用该按钮真实选择器、实际加载/滚动完成条件。失败结果和截图仍在各 attempt 中，没有把失败算通过。
