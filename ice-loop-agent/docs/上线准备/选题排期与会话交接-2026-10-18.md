# 选题排期与创作会话交接（2026-10-18）

本批继续仅在 E 盘工作区开发和验证。完整可分发桌面 Agent 的目标保持进行中，本报告不代替真实模型质量及安装升级验收。

## 用户可见流程

新工作台左栏、开始指南和命令面板新增“选题与排期”。面板按需载入，保留 Radix 弹窗/标签页、现有按钮与加载反馈，使用品牌暖白、墨黑和信号蓝。

1. **本期创作**：默认使用当前栏目真实已发布期号 + 1，显示已有同期待写稿、此前五个不同期号的完整正文与全部标题数量。可以手工选择 1–9999 期，不限十篇。
2. **标题来源**：采用对应期的预设标题、自己填写标题，或先在创作对话中与 AI 讨论选题。预设标题、内容要点、读者收益与下期预告均可修改。
3. **大纲文档**：读取 Markdown/TXT/DOCX，或填入、复制示例；示例包含第11期和第100期。先解析，逐项修正栏目、期号、标题和要点，也可以取消保留。导入预览每页8项，已存期题每页10项；跨页保留修改。已有期题变更必须明确勾选覆盖，已有文章与会话不随大纲更新改写。
4. **发布记录**：逐篇登记实际状态和日期，或快速登记已发布进度；未来日期拒绝。有效进度仍取逐篇已发布记录与快速进度的较大值，不把草稿猜成已发布，也不向微信发送任何内容。
5. **确认并带入对话**：先由后端确认期号、标题与依据，再创建会话并预填可编辑要求。此操作不自动调用模型、不创建制作任务，也不登记发布。
6. **显式生成与保存**：用户发送后才调用配置的写作模型，产生候选初稿；用户决定是否保存与提交审阅。草稿保留所选栏目和期号，显示在左栏原有草稿箱。

关闭/Esc/全局切换会保护尚未确认的大纲与选题。忙碌时禁用重复操作，显示实际阶段；读取文档后不会立即保存。切换到其他公众号时不接纳旧账号迟到的发布记录请求。

## 修复的根因

之前的指南只把栏目传入 `chat.create`，没有绑定手选期号；后续请求会根据当时发布进度重新计算期号。现在通过已确认 `publication_plans` 引用创建会话，在 `creative_conversations.target_json` 保存服务端读取的确认快照，无需新增数据库列。

新建时校验账号、栏目、确认哈希、历史版本及预设题目版本；客户端不能自行塞入可信的确认字段。创建请求的幂等指纹包含计划身份，同一请求重试仍取原会话，不能把同一请求标识改用于其他期题。网络失败保留原确认/创建请求身份，避免回执丢失后重复创建。

本次创作以已确认期号读取此前五篇正文和全部历史标题；之后发布进度变化不会把它从第100期换成第13期。对于已手工确认/从大纲选定的初稿标题，即使模型另起标题，也在候选落盘前统一使用用户确认的标题及正文 H1；不改代码围栏内的注释。保存后进入既有草稿编辑/人审流程。

另修复跨期预告：从第11期页面选用第100期时，只能查找本栏目第101期或使用第100期明确写下的预告，不再错误带入第12期标题。

`history.progress` 新界面写入带 `context_hash`，在数据库事务内比较并更新；过期状态不能覆盖新进度。历史读写显式账号与当前账号不符时拒绝。手工确认标题还增加单行检查，避免换行注入额外 Markdown H1。

## 内存与构建的实际边界

原生在真实 SQLite 中增加到 **1026条**期题，界面每页只渲染10行。预热3次后再次开关面板12次，并以 CDP 显式GC后取样：V8已用堆 6,418,408→6,648,620 字节，增长230,212字节（约0.23MB）；DOM始终340节点，事件监听始终343个。结果保存在最终原生JSON的 `memory`。这只证明该样本下反复关闭面板的回收行为，不是整个 Electron进程只用6MB，也不是长时压力已全部完成。

已存期题仍通过旧 `outlines.list` 一次返回全部元数据，本次有界的是 DOM渲染、导入页和卸载释放；后端列表分页与按期精确查询仍可继续优化，不能声称传输也已分页。

构建入口为513,816字节，实际静态JS闭包为569,193字节，见 `editorial-bundle-analysis.json`。排期面板不在启动闭包内。旧日志入口/client/toast为分散输出，新构建归并了共享部分，不能将入口单文件变化直接等同内存或启动时长变化；此处不宣称总RAM或启动速度改进。
