# 真实供应商端到端实测（2026-11）

**目的**：用真实国内模型和真实 Key，在自己的公众号上从选题到导出完整做 2–3 篇文章，回答一个问题：**产出能不能直接用，哪里卡住了**。结果用来决定下一阶段做什么，优先于继续做界面细节和边界加固。

## 1. 三篇实测文章怎么选

尽量覆盖不同的入口，而不是做三篇相似的：

| 篇 | 场景 | 走的入口 | 例子 |
| --- | --- | --- | --- |
| A | **系列续写**：已有栏目、有历史文章 | 选题依据（前五期正文 + 全部标题）→ 初稿 | 某栏目的下一期 |
| B | **从想法开始**：只有一个观点或素材 | 创作对话"讨论"→"初稿" | 一个你最近想写的话题 |
| C | **改旧文**：已有一篇不满意的稿子 | 编辑正文 / "改稿"模式 + 修改提案审阅 | 一篇存稿或已发布文章的改版 |

时间不够就先做 A，它覆盖的链路最长。

### 文章质量检查（初稿和终稿各看一次）

- [ ] 符合本栏目的读者定位和语气（对照公众号与品牌设置）

- [ ] 事实、代码和示例正确；代码能跑
- [ ] 结构完整：标题、开头、正文层次、结尾、下期预告（如栏目要求）

- [ ] 长度合适，不需要大幅删减

## 5. 做完之后

把问题记录按严重度排序，回答下面三个问题，作为下一阶段的输入：

1. **最大的阻断或严重问题是什么？** → 下一轮第一优先。
2. **哪个阶段最耗时、最不满意？** → 决定是改提示词/上下文（产出质量），还是改流程/界面（操作成本）。
3. **哪些功能这次根本没用到？** → 是否在发布前冻结或简化。

把填好的本文件和问题截图交给下一轮迭代，作为新的验收依据。没有在真实环境里复现过的问题，不要靠猜测修。
