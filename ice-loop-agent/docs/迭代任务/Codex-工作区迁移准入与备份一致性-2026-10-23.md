# 工作区迁移准入与备份一致性

本轮继续通用 Windows 桌面版的功能可靠性与可恢复性。版本保持2.0.0-beta.2，没有新数据库迁移，没有修改历史迁移函数，未提版、提交推送、打包或覆盖个人安装。

## 迁移准入与失败关闭

原先 Store 在数据库已达当前版本时跳过迁移审计，只有显式 run_migrations 或备份检查才发现 checksum 漂移。现在先执行只读准入，再进入日志模式、基表和迁移写入流程；当前版本也检查。较新 user_version、未知记录、缺少迁移历史/中间记录、记录类型伪装、v18+ 校验/说明不一致均在主动改库前拒绝。已有合法完整历史但版本号被旧工具调低时，仍支持只向前修复；不会重跑已经记录的迁移，也不会改写旧记录。

已用文件 SHA 与表/版本检查复现并验证：旧直接迁移入口遇到未知记录9999时会先完成许多迁移，再因最终 PRAGMA 无映射而报错，原库字节已改变。新入口在创建跟踪表或应用迁移前拒绝。对调用方已有未提交事务的请求，旧入口的 BEGIN 失败后还会 ROLLBACK 掉调用方编辑，探针显示 in_transaction=false、文字退回原值；现在明确要求调用方先结束事务，原编辑保留。

Store 初始化的任意异常会关闭所属连接，旧基线备份连接也改为显式关闭。正常最新版连接仍只读准入，不引入迁移写锁；另一个 writer 持有 BEGIN IMMEDIATE 时，100ms busy timeout 的新读连接仍可打开。

早期10–17迁移保留原有兼容政策，校验差异明确列为 legacy_unverified，预览说明范围。没有把旧 co_code-only 记录悄悄改成新校验值。v2_schema.py 字节摘要与上轮完全一致；真实已发布构建之间、跨解释器版本的完整 checksum 过渡仍需按实际样本继续验收。

## 备份包与实际恢复字节绑定

原先 inspect_backup 先打开ZIP校验，关闭后重新按路径算hash；在校验期间原地改写包，可使旧预览摘要配上新文件hash。改为同一文件句柄先算摘要、读取校验，再对同一文件复算。恢复也在暂存目录完成后、发布前复查原包摘要。

每一份实际解压文件都按清单重新核对大小和SHA256，流式读取并限制大小。设置与验证副本数据库也核对实际读取字节。新回归在第一次校验后注入不同读取内容，即使磁盘ZIP摘要未变，仍拒绝发布；不以ZIP的CRC替代SHA256。恢复失败只清理本次新建的暂存目录，原工作区和其他目录保留。

原先旧 schema 仅在 checked.db 临时副本中升级，实际恢复目录发布时仍可能是旧版本。现在在真实暂存目标内完成迁移、路径重定位和证据检查，全部成功后才 rename 发布；写入当前程序版本的迁移记录。目标迁移故障注入明确不发布目录。恢复结果显示已完成的 schema 变化。

## 真实历史任务重试兼容

额外读取本地 Git 的真实历史提交6b5d63c，旧源码的 TaskQueue.enqueue 使用 str(hash(JSON))，随进程变化且与当前规范JSON SHA256不同。仅保持旧任务行并不够：相同请求升级后被误报为输入冲突。已用原旧源码生成的任务真实复现。

现在仅在同账号、同kind、同幂等键、已存负载与请求完全一致，且旧指纹匹配已知数字格式时，事务内按原hash条件转换为稳定SHA256。返回原task_id，状态、结果、租约、attempt和时间均保留；不创建任务、不重新排队、不调用模型。不同输入、当前64位SHA不一致继续拒绝。测试覆盖终态、跨账号/类型与两个连接同时重试。
