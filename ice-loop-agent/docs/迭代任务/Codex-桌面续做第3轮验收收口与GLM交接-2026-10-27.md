## 本轮最小加固

静态核对发现旧条件 `samples.length >= 2` 只保证 trace 开始后有采样；较慢 RPC 期间可能已满足，不能保证样本晚于回读和渲染。这是测试观察语义的缺口，**不是已复现产品瞬消**；原样旅程仍如实记为通过，没有放宽或改写失败口径。

`reading-resume-blocker.cjs` 现先保存原 tabs/dialog/editor 与焦点、启动 trace，再点击已有工作台的“刷新配图”。必须观察到成功的 renderer `jobs.get`，其 job/article/account、正文 hash 与 slot ID 顺序和真实服务前置读取一致。`reading-lifecycle-browser.cjs` 仅在请求审计摘要增加 article_id；未改变服务数据或响应交付。随后仍调用真实的 completed `jobs.resume`，要求非注入的服务拒绝和完整前后身份/事件/调用账本保持。

回读完成后等待两次 requestAnimationFrame，记录浏览器 `postRenderAt`，在 2 秒有界窗口内要求出现 `sample.at > postRenderAt`。结果保存 `firstPostRenderSampleAt`，原无非预期移除和节点/焦点身份断言同时保持。终版首个后续样本晚 **44ms**；独立 blocker 段 3 个样本、0 移除，覆盖一次刷新/拒绝/渲染窗口，不代表长期稳定性。

## 同 job 消费者自然恢复的接续边界

对当前原生/浏览器入口及新候选路径的核对如下；除了已实测的拒绝/刷新，其余条件属于源码核对，不冒充已执行的恢复旅程。

| 入口 | 已核对条件 | 本轮证据及未决 |
| --- | --- | --- |
| 编辑器 → 工作台 → jobs.resume | 三个现有编辑入口要求 completed；service 拒绝 completed/cancelled，引擎直接返回终态 | 同一 `job-kb-done/art-kb-done` 的 renderer 刷新和真实拒绝通过；没有消费者改图位 |
| approvals.decide / execution.approve | 保存决定后调用 `_start`，由独立 executor 执行；execution 还要求 verify_code 的 awaiting_user/failed/paused | 不能按 RPC 名称推断来自消费者；本轮未为补证绕过 executor 或确认代码执行 |
| backup.resume_queue | 当前账号及 input_hash 匹配，task 必须 paused/RESTORE_REVIEW；仅将 paused 的绑定 job 改 queued | 是消费者入口候选，但当前夹具没有该任务/绑定。completed job 不会因此变回 asset_plan，实际恢复/窗口保持仍待验证 |
| worker 对账/重认领 | paused job 保持 paused；completed job 即使进入队列，引擎仍返回终态 | 不能把终态 task 对账宣称配图节点重跑 |
| 正文保存 / image_only | 正文保存不改变 completed 终态；补图使用独立 workflow/spec | 不能冒充同一 production 消费者改图位 |
