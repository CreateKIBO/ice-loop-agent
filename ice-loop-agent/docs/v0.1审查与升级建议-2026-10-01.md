## 3. 优先修复的实现问题

P1 表示应在日常真实写作、HTTP 接入或自动生图对应功能上线前解决；P2 表示可在下一轮完善。以下同一标题中可能合并多个相关探针，不代表 14 个互相独立的大模块都需要重写。

### 3.1 [P1] 正式模型路由会使用 Mock，审核恢复也会切换供应商

位置：[cli.py:41](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/cli.py:41)、[cli.py:66](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/cli.py:66)、[cli.py:153](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/cli.py:153)。证据 R01。

`qwen-deepseek` 实际构造 `[qwen, deepseek, mock]`，通用路由把 Mock 放进写作的回退链，审稿主模型还直接取列表最后一项，即 Mock。注释所说“Mock 不参与写作”没有被程序落实。两个真实供应商认证失败时，离线探针仍获得 `adapter=mock` 的成功正文。

此外，`approve` 与 `resume` 默认 `--provider=mock`；`_resume_app` 按本次命令参数重建模型配置，没有从任务保存的配置恢复。这会让真实任务在审核后继续生成 Mock 内容，或者停在不同内容的新审核门。任务只保存路由 ID，没有保存完整 profile 与能力快照。

**修复建议：**正式模式只允许明确配置的真实供应商，演示模式另设显式入口；审稿主模型与写作模型独立配置。创建任务时冻结路由、完整 profile、model_id、端点、能力快照、非秘密凭据引用和提示词版本。恢复时读取任务快照；主动换模型必须生成新的配置版本并展示影响，不能根据 CLI 默认值改变任务。

**验收：**两家真实模型都不可用时任务明确失败或等待用户；任何正式角色都不能返回 Mock；跨进程批准和恢复仍使用原配置；无 Key 时不产生伪装成真实生成的文章。

### 3.2 [P1] 审核门批准之后会重新请求模型

位置：[nodes.py:151](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/workflow/nodes.py:151)、[nodes.py:211](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/workflow/nodes.py:211)、[nodes.py:420](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/workflow/nodes.py:420)。证据 R02。

topic、outline、final_title 都先调用 `generate`，随后才进入审核。暂停分支没有把该候选写入可恢复状态；批准后重入节点又生成一份候选。固定 Mock 恰好每次相同，因此现有测试通过；真实模型只要换一个词，hash 就改变，程序又要求审核。

探针中第一次批准 `candidate-1`，恢复后生成 `candidate-2`，任务仍停在 topic。这也会重复消耗模型请求。

**修复建议：**把“生成候选”“等待决定”“采纳该候选”拆成三个持久状态。候选修订及 hash 必须在暂停前提交；恢复后只读取已批准的原修订。只有用户点击“重新生成”才再次调用模型，并明确作废受影响的后续决定。用户选择也应单独记录，避免修改批准 payload 后留下旧 content_hash。

**验收：**非确定模型完成一次候选生成后，批准不会再次请求；等待中刷新不会创建新审批；重启后仍可批准原内容；否决后可编辑或重新生成，而不是仅得到永久失败。

### 3.3 [P1] 修订后的代码可以沿用旧运行证据并导出

位置：[nodes.py:338](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/workflow/nodes.py:338)、[exporter.py:117](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/export/exporter.py:117)、[nodes.py:553](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/workflow/nodes.py:553)。证据 R06。

审校阶段让模型输出整篇修订正文，随后只重新做文章规则检查，没有验证代码和输出是否变化。导出源码从当前 `integrated_md` 的代码块读取，但 RunRecord 仍来自先前代码。探针把 `range(1, 6)` 改成 `range(1, 7)`，最终仍可 `ready_for_publish`，导出代码 hash 与运行记录不相同。

提示词中“不得修改代码”不能代替程序校验。另一个静态发现是输出回填忽略 `RUN_OUTPUT` 标签里的 run ID，使用顺序 `ordered[idx]`；标签错序或遗漏会造成错误关联，目前未单独加入探针。

**修复建议：**代码块建立稳定 block_id，RunRecord 绑定 code_hash、stdin_hash、运行环境和修订。审校优先返回 prose patch，代码与真实输出作为受保护块。任何代码或输入变化立即作废对应执行记录，回到验证节点。回填按 marker 中的 run ID 查找；未知、重复、缺失引用都应报错。导出前再比较当前源码 hash 与 RunRecord，不依赖“过去验证过”的状态。

**验收：**修改一行代码后不能沿用旧输出；移动代码块不会错配；输出标签错序仍能正确回填；没有合法运行证据的源码不能进入就绪包。

### 3.4 [P1] 图片就绪条件不可靠，换图后的选中候选没有被使用

位置：[nodes.py:557](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/workflow/nodes.py:557)、[engine.py:233](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/workflow/engine.py:233)、[exporter.py:72](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/export/exporter.py:72)、[tapnow.py:17](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/providers/tapnow.py:17)。证据 R04、R05、R07。

当前把所有 accepted 候选相加，与必需图位数量比较。一个图位导入四次就能“补足四图”，即使另外三个仍为空。探针得到 `ready=true`，实际仅导出一张图，正文仍有占位符。

导入时数据库保存新的 `selected_candidate`，state.json 没有同步；导出却读取 state 里的图位，再取第一个 accepted 候选。因此用户换图后，导出的可能仍是旧图。另外 selected_candidate 按类型是 ID 字符串，导出代码却调用 `selected.get(...)`；如果将新图位同步到 state 而不同时修正这里，会引发异常。这一字符串路径是静态发现。

图片检查只识别魔数。只有 8 字节 PNG 文件头也被判有效。候选引用外部原路径，文件之后被删除或替换时，就绪统计不会重新检查实际文件与登记 hash。

**修复建议：**每个 required slot 必须绑定一个确切、已采纳、可解码且 hash 一致的候选。查询候选使用 ID；统一由数据库读取图位状态。导入时复制到运行目录的受管理资产区，保留原始文件与尺寸信息；导出前校验存在、内容 hash、可解码、必要尺寸和正文引用。真实解码可放在独立图像组件，不必让工作流引擎承担所有细节。

**验收：**四次导入同一图位仍待补图；换图后导出最新选中图；损坏、缺失、篡改文件不能就绪；全部必需图位完整时才允许清除正文占位符。

### 3.5 [P1] 模型可以自己宣布事实已经核验

位置：[nodes.py:184](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/workflow/nodes.py:184)、[facts.py:48](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/rules/facts.py:48)。证据 R10、R11。

research 节点只在没有 status 时派生状态，因此模型返回 `status=verified` 会被原样存储。事实规则接受 verified 文本，却不核查来源存在、证据、时间或授权审核者。探针中没有任何 source_ids 的 `Python 3.12` 断言仍被存为 verified 并通过事实检查。

即使 tier=1 也只说明来源等级，不能说明该页确实支持该断言。当前没有真实网页抓取步骤；材料中只给 URL 或摘要，不应视为已经完成事实核验。无 source_id 的材料还会在入库时生成随机 ID，在后续映射里使用 `src-user`，存在引用不一致的静态问题。

**修复建议：**模型只能提出断言和证据候选，不能写核验状态、核验时间或审核者。来源 ID 先由系统规范化，核对引用存在；保存原文片段、URL、抓取时间、hash、主张与证据的对应关系。程序检查加人工/专门核验步骤才可升级 verified。发布当天的敏感断言需要明确的有效期规则，不能靠正文里出现“以官网为准”代替。

**验收：**模型自报 verified 被忽略；无来源、无支持片段和过期证据不能通行；同一版本号在不同上下文出现不能仅凭数字互含判定已核验。

### 3.6 [P1] 文章截断被当作成功，当前流式没有实时显示

位置：[transport.py:160](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/llm/transport.py:160)、[transport.py:188](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/llm/transport.py:188)、[router.py:104](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/llm/router.py:104)。证据 R08。

传输先 `resp.read()` 获取全部内容，再解析 SSE，增量回调只有结束后才发生；路由也没有把增量连接到工作流事件。SSE 没有终态或 DONE 时，把缺失 finish_reason 补成 stop。普通响应的 length 结束也不会被路由拒绝，截断文章仍返回成功。

**修复建议：**逐块读取并解析事件，分别处理正文、用量、错误与终态；正文增量发送给桌面，完整候选只在结束成功后提交。截断、断流和过滤保留 incomplete 修订，不能写成成功正文。记录真实 finish_reason。增加读超时、整体截止时间、最大响应体和取消信号；取消仅表示本地停止时明确记录远端费用未知。

**验收：**首段在响应结束前可显示；中途断线不提交完成修订；length 不通过；用量尾事件缺失记 unknown；多个候选的流不能拼成一篇文章。

### 3.7 [P1] 模型调用预算是配置字段，没有实际执行

位置：[engine.py:56](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/workflow/engine.py:56)、[router.py:173](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/llm/router.py:173)。证据 R03。

`max_model_calls` 保存到任务里，没有在调用之前扣减和拒绝。探针设为 1，仍完成 11 次已登记请求。JSON 修复直接调用 adapter，没有单独登记 usage；一条请求还可能发生解析修复、schema 修复和多次重试，实际用量比主调用记录更多。当前重试也没有退避。

**修复建议：**统一所有真实网络调用经过 InvocationService，在发送前事务预留次数与费用估算；调用、回退、修复各有独立 invocation_id。记录开始、结束、usage、是否不完整和 finish_reason；失败且计费未知时不记零。429 和可重试服务错误增加有限退避、随机抖动与任务整体时间上限，避免整条回退链无限消耗。

**验收：**上限 1 时第二次调用发送前被阻止；JSON 修复也计数；重启不重置预算；用量未知与零用量分开；两条并发请求不能越过同一预留上限。

### 3.8 [P1] 结构化业务字段没有被要求必填

位置：[router.py:235](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/llm/router.py:235)、[nodes.py:138](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/workflow/nodes.py:138)。证据 R09，结合业务节点静态检查。

简化 schema 支持 required，但多数节点 schema 没有设置它，因此 `{}` 可以通过类型校验。title_workshop 后续直接访问 candidates，空对象会变成 KeyError；推荐序号、候选非空、分数范围、source_ids 与 risk_type 也缺少完整业务约束。修复提示词在 schema 不匹配时没有携带完整目标契约，增加真实模型成功恢复的难度。

**修复建议：**保留现有校验器或引入独立校验组件均可，关键是为每个节点建立明确契约：必填、非空数组、索引范围、枚举、引用存在、分数上下限和最大字符串长度。模型输出不得包含有权限含义的核验字段。修复请求携带原契约和校验错误，严格限制次数，并进入调用账本。

**验收：**空 JSON、空标题数组、越界推荐位、不存在的来源引用都在节点边界产生可解释错误，不在后续崩成 Python 异常。

### 3.9 [P1，服务/自动生图上线前] 数据库跨线程与发送租约问题

位置：[server.py:19](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/server.py:19)、[store.py:197](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/domain/store.py:197)、[operations.py:84](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/ledger/operations.py:84)。证据 R13、R14。

FastAPI 服务在工厂里创建一个 Store，让同步路由共享该连接。FastAPI 的普通 def 路由在线程池执行，见[官方并发说明](https://fastapi.tiangolo.com/async/#path-operation-functions)。本次直接跨线程调用现有 Store 得到 ProgrammingError；这说明当前连接设计不适合该接入方式，尚未执行完整 HTTP 测试。

发送租约先读取 prepared，再另行更新 sending，没有条件更新与事务。用两个独立 SQLite 连接同步读取，两个调用都成功取得 sending 租约。此时唯一 operation_key 并不能阻止两个 worker 对同一操作各提交一次生图。

**修复建议：**工作流 worker 独占自己的连接，API 使用自己的短连接或查询通道；正式任务放入后台队列，HTTP 立即返回 job_id。不能只关闭 check_same_thread 后共享所有写操作。领取任务和发送操作使用原子条件更新，检查 rowcount；预算判断与操作插入放进同一事务。审批和事件序号分配也纳入并发设计，添加单篇任务 lease 和心跳。

**验收：**HTTP 查询、审核、恢复并发执行无线程异常；重复 resume 不并发生成；两 worker 同时领取只成功一个；未知发送仍先对账。本地 API 上线还需回环绑定、主进程会话 token、请求校验和生命周期清理。

### 3.10 [P1/P2] 失败不落终态、检查点写入不具备崩溃恢复保障

位置：[engine.py:168](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/workflow/engine.py:168)、[engine.py:284](G:/05-兴趣项目/gonzhonhao/wechat_agent/ice-loop-agent/ice_agent/workflow/engine.py:284)。异常证据 R12；检查点问题为静态发现。

引擎只捕获几类节点异常；ModelError、ExecutionError、ExportConflict、BudgetExceeded 或 I/O 异常可能直接逃逸。探针模拟认证失败后，外层得到 AuthError，但任务数据库仍是 running。桌面界面会因此一直等待。

state.json 直接 write_text，写到一半退出会留下不可解析文件。state 与 SQLite 步骤不是统一提交协议；重入具有副作用的节点还可能再次添加修订、图位或执行记录。现有“步骤复用”测试没有实际注入崩溃并检查恢复结果。

**修复建议：**已知错误统一转为稳定失败码，必要时转 awaiting_user，finally 释放租约。未知错误保留诊断并标成 internal_error，不静默成功。检查点使用临时文件、校验、原子替换与版本指针，保留最后有效版本；数据库保存匹配 checkpoint 的 hash 和步骤提交标记。节点重复执行要能复用确定的副作用 ID。

**验收：**认证、执行、导出冲突和存储异常不留下永久 running；在候选生成、批准、执行、导出前后分别强制退出，重启后无重复请求、无重复资产、无丢失批准。

这些项目未全部逐个动态复现，作为下一轮验收范围，不混入“14 个探针”的计数。

## 5. 下一版最有价值的产品升级

### 5.1 第一优先：桌面里的审阅与局部修订

独立桌面程序是已确认需求，应在可靠引擎基础上优先交付。继续采用原设计文档的桌面壳与 Python sidecar，保留当前 Python 模块；暂时没有必要为了更换 Agent 框架而重写工作流。

第一版桌面工作台建议包含六个区域：

1. **任务创建**：栏目、题目、素材、上一篇练习、下期预告、文章长度和本次预算。默认不读取整个磁盘作为上下文。
2. **文章与审核**：选题、骨架、标题候选都能编辑后批准；正文 Markdown 编辑与手机阅读预览；展示修订 diff 和改动原因。
3. **运行与证据**：执行代码、输入、真实输出、环境、断言来源集中查看；自动核对 code_hash；阻断项可直接定位正文。
4. **配图工作区**：按图位显示候选、选中图、提示词、引用位置；换图只替换该图位，重新生图作为新的计费候选。
5. **模型设置**：国内供应商、模型 ID、端点、连接测试、角色分配、回退、思考策略与预算；后台保管凭据，日志中仅存引用。
6. **任务与导出**：实时节点进度、暂停、取消、恢复、错误详情、草稿包/就绪包区别；打开文章目录与展示尚未完成的事项。

局部修改需要明确依赖关系：改 prose 重新审稿；改代码重执行；改事实重核验；改标题作废对应封面确认；换图片不重新写整篇文章。这比增加泛用聊天 Agent 更贴近日常公众号制作。

### 5.2 第二优先：国内模型的质量和稳定性

先在两家已配置供应商上完成真实文本、结构化、流式、异常与回退验收；再扩展其他模型。供应商适配数量不能直接说明文章质量。

使用 PY/JV/AI/WK 四类任务做小样本人工评测，记录：是否兑现标题承诺、零基础是否能跟着做、事实能否追溯、演示代码是否可运行、系列练习是否衔接，以及人工修改花费。已存稿作为样例，不能直接当作无误标准答案。

规划与格式任务可走轻量模型；正文和技术审稿按实际样本结果选择。不同模型交叉审稿可提供另一视角，但最终的源码、事实、预算和发布资格由程序与用户决定。提示词版本化后比较改动收益，避免随意添加越来越长的规则文本。

建议加“重写这一节”“解释得更简单”“保留事实仅调整语气”等局部操作，并保护代码、已核验数字和真实输出；保留完整修订，允许撤回。

### 5.3 第三优先：TapNow 浏览器完成一张图的闭环

自动生图上线前先完成 3.9 的发送租约与预算修复。图位、候选、operation、provider_task_ref 和 asset 要有明确映射。

初次配置由用户在独立浏览器资料目录完成登录；记录实际账号、画布和配置，避免控制日常浏览器。页面操作按状态执行：打开画布 → 准备节点 → 填提示词与参考图 → 核对设置 → 批准生图计划 → 原子领取发送权限 → 单次提交 → 监控 → 下载 → 解码校验 → 候选审阅 → 绑定图位。

DOM 定位优先使用实际验证的可访问属性；Canvas 元素另做定位适配。遇到登录或验证码进入接管状态。提交之后丢失回执，保留 unknown 并对账；不能更换浏览器/MCP 通道立即再生成。MCP 后续可作为另一通道，浏览器功能仍需交付。

首个验收不必扩展多账号、多画布和无限重试，只需要可靠生成一张图，并通过“提交后关闭应用，再启动”场景确认不会重复生图。

### 5.4 第四优先：三种截图各自成立

| 类型 | 内容 | 必需证据与验收 |
|---|---|---|
| 网页截图 | 浏览器页面或某个元素 | URL、时间、尺寸、滚动/视口信息；中文/DPI/长页面验收 |
| 运行日志视图截图 | 使用 RunRecord 渲染的受控界面 | run_id、code_hash、输入和输出；明确标识来源，不能宣称是实际 IDE 终端 |
| 原生程序窗口截图 | IDE、终端或其他 Windows 应用窗口 | 窗口身份、捕获时间、DPI、遮挡状态；窗口定位与手动接管 |

建议先实现网页和运行视图截图，再实现原生程序捕获。保存原图与裁切参数；裁切不得改变错误、输入和输出的含义。日常操作可按篇决定自动截图或手动导入，不批量改写原有存稿。

### 5.5 内容资产与系列连续性

从已有文章包建立只读内容索引：栏目/期号、上一期练习、参考答案、下期预告、技术概念、发布状态、事实核验、配图状态。创建新文章时显式选定上一期，用户确认真实练习内容，模型不能凭标题猜答案。

素材检索先采用结构化字段和关键词；只有语义检索确有收益时再增加向量索引。加入相似选题提示、同一知识点的解释一致性检查、封面模板复用与待发布库存视图。缓存适用于不变的证据和规则，敏感事实的有效期不能被缓存覆盖。

## 7. 最小回归清单

- 非确定模型候选批准后不再请求；刷新等待页不新增审批。
- 正式任务中 Mock 永远不可选；批准恢复读取原模型快照。
- max_model_calls 包含失败、修复和回退；请求发送前拒绝超限。
- 断流、length、空 JSON、schema 缺字段均不作为成功候选。
- 审稿改代码后必须失效旧 RunRecord；输出引用按 run ID 查找。
- 每个必需图位独立就绪；多候选不抵消缺图；导出选中图。
- 损坏、缺失、被替换的图片或外部修改的源码不能被静默接受。
- 模型自报 verified 无效；敏感断言必须有真实来源与核验记录。
- 认证/执行/导出异常落可解释终态；检查点损坏可恢复到最后有效版本。
- 两个 worker 不能同时提交一项操作；重复 resume 不能并发写作。
- 桌面启动、退出、恢复、取消和数据库升级不丢任务。
- 干净环境安装能找到规则资源；数据目录仍遵循 G 盘要求。

最先处理 3.1–3.5，能直接改善真实文章生产的可信性；随后完成预算、流式与恢复，为桌面交付打基础。新模型、更多生图通道和高级内容检索在这些验收成立后逐步加入。
